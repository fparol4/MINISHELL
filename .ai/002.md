# Port Plan: `main` pieces into `dev/merge`

## Goal

- Keep `dev/merge` as the integration branch.
- Do not git-merge `main` directly.
- Move code portion by portion from `main` into the executor-based tree.
- Keep each step small enough to compile or diagnose before moving to the next one.

## Pre-Work

### 1. Typing Corrections

- Normalize shared type names before importing larger modules.
- Check enum names used by executor and parser, especially node and redirection types.
- Decide which public names survive in `dev/merge`.
- Avoid duplicate definitions for `t_redir_type`, `t_node_type`, parser nodes, and shell-wide structs.
- Keep executor-facing names stable where possible to reduce runner changes.
- Fix obvious typos in existing paths, module names, and headers only when they block integration.

### 2. Missing Libft Functions

- Compare functions used by `main` lexer/parser against the `dev/merge` libft.
- Add only missing functions required by the next porting steps.
- Prioritize functions used by scanner, lexer, parser, and parser tests.
- Expected candidates include allocation/string/list helpers used by `main` code.
- Update libft headers and makefiles together with each added function.
- Compile libft alone after this step.

## Port Order

### 1. Core: `source/core`

- Create the application start point under `source/core`.
- Centralize shell initialization, heap allocations, env initialization, and cleanup ownership.
- Keep readline loop orchestration here, not inside lexer/parser/executor modules.
- Define the intended runtime flow: input -> lexer -> parser -> executor -> cleanup.
- Integrate existing env initialization from executor branch before connecting parser output.
- Make core compile with current executor behavior before importing lexer/parser logic.

### 2. Lexer Module

- Port scanner/infra pieces required by lexer first.
- Port public/private lexer headers into the `dev/merge` header style.
- Port lexer implementation files after their dependencies compile.
- Keep lexer output shape close to `main` unless it conflicts with shared project types.
- Preserve token expansion metadata because parser and heredoc behavior depend on it.
- Add a small lexer-only test or temporary debug path if needed.
- Compile after lexer is linked, before starting parser port.

### 3. Parser Module

- Port parser headers and implementation after lexer builds.
- Decide whether parser result should become executor-native or stay as parser AST.
- If parser keeps `t_ast`/`t_command`, add a thin converter to executor `t_exnode`.
- Map node types explicitly: `NODE_CMD` -> `CMD`, `NODE_PIPE` -> `PIPE`.
- Map redirection types explicitly: `REDIR_IN` -> `IN_F`, `REDIR_HEREDOC` -> `IN_H`, `REDIR_OUT` -> `OUT_T`, `REDIR_APPEND` -> `OUT_A`.
- Convert parser redirection arrays into executor linked lists in the original order.
- Preserve `expand` on redirections, especially heredocs.
- Connect parser result to executor only after parser cleanup/error paths are stable.

## Validation Gates

- After pre-work: libft and executor still compile.
- After core: app starts, initializes env, and exits cleanly.
- After lexer: input can be tokenized and freed without leaks/crashes.
- After parser: input can produce an AST or syntax error and be freed safely.
- After executor connection: simple commands, pipes, redirections, heredocs, and `$?` should be tested manually.

## Risk Areas

- Duplicate struct/enum definitions across old executor headers and new parser headers.
- Include path churn between `headers/`, `includes/`, `source/`, and `src/`.
- Libft function differences between branches.
- Redirection storage mismatch: parser array vs executor linked list.
- Expansion ownership: lexer/parser store `expand`, executor currently expands argv and heredoc lines.
- Cleanup ownership after converting parser AST to executor nodes.
