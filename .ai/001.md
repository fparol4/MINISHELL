# Incremental Port Overview: `main` into `dev/merge`

- We will not do a direct git merge from `main` into `dev/merge`.
- `dev/merge` is the integration branch and currently starts from the executor branch state.
- The plan is to move working pieces from `main` into `dev/merge` step by step.
- Each moved part should be adapted to the executor branch layout instead of replacing the whole project tree at once.
- This avoids the large structural conflict where `main` replaces `headers/`, `source/`, `tests/`, and `Makefile` with `includes/`, `src/`, `tester/`, `infra/`, `libft/`, and `makefile`.

## Current Branch Roles

- `dev/merge`: target branch where we will assemble the final minishell.
- `dev/fabricio`: executor/env/builtin/runner implementation source.
- `main`: lexer/parser implementation source.
- `dev/merge` and `dev/fabricio` point to the same executor commit at the moment.

## Parser Output Difference

- Executor side expects `t_exnode` from `headers/minishell.h`.
- `t_exnode` has direct fields: `type`, `args`, `redir`, `left`, `right`.
- Executor node types are `CMD` and `PIPE`.
- Executor redirection types are `IN_F`, `IN_H`, `OUT_T`, `OUT_A`.
- Executor redirections are a linked list: `t_redir { type, target, expand, next }`.
- Parser side returns `t_ast` with `root`, `size`, `error`, and `error_type`.
- Parser root is `t_command`, currently defined in `includes/private/parser_internal.h`.
- Parser node types are `NODE_CMD` and `NODE_PIPE`.
- Parser command data is stored inside `cmd->t_define.simple` or `cmd->t_define.pipe`.
- Parser redirection types are `REDIR_IN`, `REDIR_OUT`, `REDIR_APPEND`, `REDIR_HEREDOC`.
- Parser redirections are stored as an array: `t_redir *redirs` plus `redir_count`.
- Parser redirection target field is `file`; executor expects `target`.

## Recommended Port Order

- First port the shared parser/lexer dependencies needed by `main`: scanner/infra helpers, token types, syntax errors, and required libft helpers.
- Then port lexer files and make them build in the `dev/merge` layout.
- Then port parser files and expose a stable parser result type usable outside parser internals.
- Then adapt parser output to executor input, either by changing executor to consume `t_command` or by adding a small converter from `t_ast`/`t_command` to `t_exnode`.
- Then connect the readline loop: input -> scanner -> lexer -> parser -> executor -> cleanup.
- Finally port or rewrite tests around the integrated flow.

## Integration Notes

- Do not replace the whole executor tree with `main`; move only the needed lexer/parser pieces.
- The main compatibility problem is AST shape, not pipe semantics.
- Simple commands map cleanly: parser `simple.args` corresponds to executor `args`.
- Pipes map cleanly: parser `pipe.left/right` corresponds to executor `left/right`.
- Redirections need explicit conversion because enum names, target field name, and storage type differ.
- Heredoc expansion must preserve the parser-provided `expand` flag because executor uses it when reading heredoc body lines.
- Build updates should be done incrementally after each ported module so breakages stay small.
